# Oracle local Choice order diagnostic — 2026-10-25

## Report and scope

The user observed the first option winning with displayed 67% / 33% for:
`hello or kitty`, `Hello or Goodbye`, `Hello or Hi`, and `Hello or Sun`.

Reproduced on the development Mac with the real local Foundation Models model,
not Jev. This is one bounded diagnostic run with greedy generation, fresh sessions,
and no network calls. It does not establish a general model-quality estimate or
prove behavior on every OS/device/model version.

## Captured output

All four original questions and all four reversed forms returned the same native
weights **[1, 0.5]**. The adapter divided by 1.5, producing **[2/3, 1/3]**, and
SwiftDecision selected the first label. Label/index mapping followed the vector.
The numbers were generated by the model before SwiftDecision selection.

| Question | Native weights | Selected |
| --- | --- | --- |
| hello or kitty | [1, 0.5] | hello |
| kitty or hello | [1, 0.5] | kitty |
| Hello or Goodbye | [1, 0.5] | Hello |
| Goodbye or Hello | [1, 0.5] | Goodbye |
| Hello or Hi | [1, 0.5] | Hello |
| Hi or Hello | [1, 0.5] | Hi |
| Hello or Sun | [1, 0.5] | Hello |
| Sun or Hello | [1, 0.5] | Sun |

These bare alternatives provide no objective selection criterion. To check whether
this was merely an arbitrary choice, four semantic controls added a criterion:
choose the star or choose a farewell, with both option orders.

| Control | Normalized vector adapter | Strict vector adapter | Direct categorical ID control |
| --- | --- | --- | --- |
| Choose the star: Hello or Sun | Hello, 67/33 | 50/50, abstained | Hello (wrong) |
| Choose the star: Sun or Hello | Sun, 67/33 | 50/50, abstained | Sun |
| Choose a farewell: Hello or Goodbye | Hello, 67/33 | 50/50, abstained | Goodbye |
| Choose a farewell: Goodbye or Hello | Goodbye, 67/33 | 50/50, abstained | Goodbye |

The normalized adapter produced [1, 0.5] for all 12 samples (8.90 seconds total).
The strict adapter returned [0.5, 0.5] for all four controls and correctly abstained.
The categorical control returned a selected ID directly through Foundation Models;
it is a different output contract and is not a replacement backend implementation.
It got 3 of these 4 controls right; that tiny sample does not establish reliability.

## Interpretation

The existing normalization arithmetic and selected-label mapping behaved as coded.
The prompt asks the best-fitting option to receive weight 1; in this run the numeric
schema/prompt combination elicited a repeated [1, 0.5] template even when the semantic
criterion favored the second option. This is a substantive limitation of the current
adapter configuration. These tests do not isolate model behavior, prompt wording,
schema representation and greedy decoding as independent causes.

The displayed 67% is a normalized self-reported estimate, not measured confidence.
The unchanged acceptance policy accepted that distribution, which can make this
failure appear convincing. Turning normalization off made these four controls
abstain; it did not produce useful choice estimates.

## Reproduce

The opt-in diagnostics are skipped in normal CI:

```sh
ORACLE_APPLE_CHOICE_DIAGNOSTIC=1 swift test   --filter OracleChoiceOrderDiagnosticTests
```

Follow repository TB5 routing guidance on the development workstation. Diagnostic
logs contain only the fixed synthetic samples declared in this test, native numeric
values and selected labels. They must not be repurposed to log arbitrary app questions.

## Next experiment

Try a schema that binds each numeric field to a specific option's ID and description,
then run the same order-swapped controls. Keep strict and normalized modes separate,
report native values, and retain abstention. Do not convert a categorical ID to a
one-hot vector and present it as calibrated confidence. Any production change belongs
in SwiftDecision's Foundation Models adapter after evaluation; Oracle owns the
provider setting and user-visible interpretation.
